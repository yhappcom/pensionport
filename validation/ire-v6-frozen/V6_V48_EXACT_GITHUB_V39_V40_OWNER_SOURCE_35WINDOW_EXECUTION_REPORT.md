## 1. 이전 단계의 병목 해결

V43·V44·V45·V47에서 실제로 읽고 의미 분류한 **35개 SRT 창·450개 잠정 발화·639개 ChatGPT 의미 항목**은 원본 SHA 검증에 합격했지만, 그동안 V39·V40 코드의 동형 **로컬 재구현(staging)**으로만 검문했다. 따라서 이전에는 'GitHub 배포 코드 직접 검증'으로 집계하지 않았다.

이번 V48에서는 GitHub 브랜치에 이미 존재하는 `ire/v6/host_semantic_custody_v39.py` 및 `ire/v6/semantic_checkpoint_v40.py`를 정확한 **원본 소스 텍스트 그대로** 소유자 비공개 컨테이너에 복원했다. `git hash-object`로 확인한 SHA는 각각 `12b38f413e0d19b35dc6d0ec4cd660d0a9a68650`, `44415ca2051396010a5ade33b7326daaebafee37`로 GitHub 원본 blob과 **바이트 단위로 일치**한다. 단, 전체 저장소를 완전하게 체크아웃하지 않고 source/codec/provisional 헬퍼 **필요 최소부분의 호환 코드**를 복원해 import했다. 보조 의존성까지 모두 Git 원본 blob이라고 주장하지 않는다.

## 2. 원본 35창 → 실제 V39 검문 → 실제 V40 SQLite commit

- 소유자 비공개 ZIP `1-100.zip` SHA256 `088869c583b2d3ed93d68e4dd5348b1f506877ea2bdc1d66466c199ec80e7716`에서 해당 #1~#5 SRT를 다시 추출하고 원본별 cue 및 전체 누적 V33 후보 ID를 재생성했다.
- 서로 중복되지 않는 **35개 창·1,400개 SRT cue**, V33 **450개 발화 후보**에 대한 **639개 의미 검토 항목**을 V37의 독립 고정 원본창/후보 SHA 및 ChatGPT 비공개 의미 주석에 대조했다.
- **실제 GitHub V39 모듈**의 `audit_host_semantic_custody_v39`를 **15개 최대 4창 그룹** 모두에서 직접 호출했다. 실제 코드의 receipt SHA **15/15**가 기존 독립 재구현의 SHA와 완전 동일했다.
- 별도 비공개 SQLite `v48_owner_private_35window_EXACT_GITHUB_V39_V40.sqlite`에 **실제 GitHub V40 모듈**의 `PrivateSemanticCheckpointV40.submit()`으로 15개 그룹을 순차 저장했다. 이벤트 SHA **15/15**가 이전 로컬 재구현 checkpoint SHA와 완전 동일했다.
- 동일 run ID/동일 데이터 재호출 **15/15**에서 idempotent를 보고했으며, 영상 5개 각각 `verify_chain()`이 원본창 소유권과 헤드 해시 체인 검사를 통과했다.
- 원본 발화 누락, 동일 후보 중복, 빈 의미 주석, 허위 금융 사실 승인, 동일 원본창 중복 저장 등 **부정 입력 검증**도 fail-closed로 확인했다.
- SQLite 파일은 **40,960 bytes**, SHA256 `fd185b72cd068b937bad4433a954df9a22af180e5d39078189ea3a8de824ccf6`. 원본 SRT/개인 검토 설명 문장은 DB에 저장하지 않았으며 비공개 소유자 파일 자체를 GitHub에 업로드하지 않았다.

이 검증으로 **이전 V43~V47의 35개 창은 정확한 GitHub V39/V40 본체를 실제 실행한 체크포인트로 승격**할 수 있다. 이전에 완료했던 별도 원장 8개 창은 이번 35개와 전혀 중복되지 않지만, **한 SQLite 원장의 동일 헤드 체인으로 합병하지 않았으므로 동일 DB 43창 저장으로 표현할 수는 없다.**
