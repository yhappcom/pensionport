## 1. 체크리스트의 법칙 — 실패하면 그 항목을 통과하기 전 다음 진행 금지

1. 12단계 / **60개 세부 항목**을 이 문서의 순서대로 실행한다. **현재 선행 항목 전체가 PASS인지** 매 작업 시작·종료 시 검사한다. 최초 상태는 **`P0-0-01=READY`**, 나머지 **59개 = `BLOCKED`**. 문서의 체크박스는 사람이 보는 표이고 **실제 완료 판정의 단일 진실값은 JSON 상태 원장**이다.
2. 상태 종류: `BLOCKED`(선행 미완료), `READY`(유일한 다음 작업), `IN_PROGRESS`(착수 보고 후 실행), `FAIL`(시험 실패), `HOLD`(자료/권한/실제 2턴 미확보), `PASS`(근거·합격·종료 보고 검증 완료). **`FAIL` 또는 `HOLD` 발생 시 같은 ID에서 원인·반례·수정·재시험을 마쳐 `PASS`가 되기 전 후속 작업 착수 금지**. 임의로 `CANCELLED`, `SKIPPED`, `NOT_APPLICABLE`, `WAIVED`로 통과하는 상태가 없다.
3. 앞선 항목이 모두 `PASS`일 때 **바로 다음 한 항목만** `READY/IN_PROGRESS/FAIL/HOLD` 중 하나일 수 있다. 그 뒤 모든 항목은 `BLOCKED`. **선행 PASS를 건너뛰어 다음 항목을 READY/PASS로 표기하면 CI 실패.** 같은 커밋에서 여러 항목을 소급 일괄 완료시키는 행위도 금지한다.
4. `PASS`에는 필수 종류의 **실제로 재조회한 증거**, SHA/경로·소프트웨어와 실제 원본 범위 구분, 실제 사용자 **착수·종료 보고**가 있어야 한다. GitHub CI PASS만으로 E2 의미 정확도, E3 사용자 2턴, E4 공식 금융근거, E5 승인 발행, P3 개인 자문을 통과시키지 않는다. ChatGPT 내부 교차검토를 독립 인간 정답으로 둔갑하지 않는다.
5. `FAIL/HOLD`를 기록하는 행위 자체는 합법이다(정직한 HOLD를 누락할 이유가 없음). 그러나 다음 항목으로 진행할 수 없다. 동일 항목을 재실행하면서 기존 FAIL/OPEN의 원인·시점·SHA를 Git history 및 새 정정 영수증으로 보존한다. 소스가 없거나 인가 없는 금융 승인은 **HOLD 유지**, 진척을 위해 가짜 통과 금지.
6. 문서/상태를 변경할 때 `python3 scripts/ire_checklist_gate.py verify --compare-parent`와 `python3 -m unittest scripts.test_ire_checklist_gate` 통과. 읽기 전용 GitHub Actions 자동 실행을 결합한다. GitHub Ruleset이 없는 현재 저장소에서는 **CI 실패가 이미 push된 커밋의 생성을 원천 차단하는 것은 아니다**. 정책 준수와 관리자 Ruleset이 추가 사전통제다.
7. 매 대화/작업 시작 전 `status` 및 `next`로 선행 상태, 이전 실패, 정확한 허용 ID 확인. 사용자의 현재 요청이 나중 단계라도 선행 단계가 미완료면 **우선 막힌 같은 항목만 수행**한다. 긴급 보안·정보유출 대응은 위험 확산 방지 목적의 예외적 안전 조치만 허용하며 단계 PASS로 자동 승격하지 않고 사유·영수증에 기록한다.

## 2. 사용자 보고 의무 — 착수 전 / 종료 직후 (둘 다 필수)

### 업무 시작 전 사용자에게 보고
새 작업을 시작하는 **매 사용자 명령(턴)**마다 코드 실행·파일 수정 전에 채팅으로 다음을 보고한다.

- **시작 보고:** 실행 ID(예: `P0-0-01`), 현재 상태(READY/FAIL/HOLD/IN_PROGRESS), 앞선 항목 PASS 개수/총 60개, 다음 항목 차단 여부, 기준 통합 HEAD·`main` HEAD·활성 브랜치 수.
- **작업 목표:** 이번 요청 범위(해당 ID), 이전 작업 실패/OPEN·원인, 수행할 수정과 예상 위험, 변경 대상.
- **합격/실패 기준:** 정확한 양성/음성 재현 시험·원본·금융 검증 범위·필수 증빙·PASS 조건. 별도 2턴이 필요하면 지금은 TURN1인지 TURN2인지 명시. 실제 사용자 TURN2를 첫 턴 내부에서 대체하지 않는다.
- 시작 보고는 텍스트로 사용자에게 실제 제시한다. Git의 `start_report`는 **보고 이력의 2차 기록**일 뿐 자체적으로 사용자가 봤다고 증명하지 않는다.

### 업무 종료 즉시 사용자에게 보고
사용자 요청에 대한 **각 작업/턴의 종료 시** 예외 없이 아래를 채팅으로 보고한다.

- **종료 보고:** 이번 ID/기준·최종 commit, 수행한 실제 변경 파일, 테스트 종류·실행 버전·성공·실패·미실행 결과 및 영수증 링크.
- **정확한 상태:** `PASS` / `FAIL` / `HOLD` / `IN_PROGRESS`를 구분. 미완료를 완료라고 쓰지 않으며, OPEN/격리/미해결 개수와 구체적 원인·개선 방안을 포함.
- **다음 작업 진입 통제:** 현재까지 PASS 건수/60, 유일하게 `READY`인 다음 ID(있을 때만), **FAIL/HOLD이면 같은 ID가 BLOCKING이며 다음 항목 진행 금지**를 명시.
- **연구 입력/승인 구분:** 실제 사용자 TURN2 여부, E1~E5 단계 상태, 실제 DB 지식 저장 건수와 기존 791 로스터 기준 실물 승인 비율을 분리. 새 브랜치 생성 또는 `main` 변경 여부 보고.
- 실패나 타임아웃으로 정식 테스트 완료가 불가능하면 해당 ID `FAIL/HOLD` 및 사용자 보고; **실행을 약속하고 응답을 종료하지 않는다**. 다음 요청에서 원인 재분석부터 진행한다.

### 보고 형식 (반드시 양쪽 모두 사용)
**착수:** `[시작] ID | 선행 PASS x/60 | 현재 READY/FAIL/HOLD | 기준 HEAD | 문제·목표 | 이번 검사·합격 조건 | 다음 단계 차단 여부`.

**종료:** `[종료] ID | 변경 커밋/파일 | 실측 PASS/FAIL/HOLD | 증빙/OPEN·원인 | PASS x/60 | 다음 허용 ID 또는 동일 ID 재작업 | main/브랜치·E1~E5 상태`.

하나의 사용자 메시지에서 여러 파일·시험을 수행하더라도 착수 보고 1개/종료 보고 1개를 반드시 수행한다. 여러 체크항목을 **다른 일자/다른 사용자 요청에서** 진행할 때는 각 업무의 시작·종료도 반복한다. 검증 자료가 2턴 요구에 해당하면 두 번째 별도 사용자 메시지에서 다시 시작/종료 보고한다.

## 4. 체크리스트 갱신 실무 절차

1. 첫 명령: `python3 scripts/ire_checklist_gate.py status` → `python3 scripts/ire_checklist_gate.py next`. 차단이면 진행하지 않는다.
2. **착수 사용자 보고** → 해당 항목 `IN_PROGRESS` 기록. 중단될 경우 그대로 유지하고 다음 턴에 선행 실패/OPEN 확인.
3. 반례 RED 시험 → 원인 분석 → 최소 수정 → 단위/통합/실물 시험 → 근거·보고 → 판정. 실패 시 `FAIL/HOLD`에 원인, 복구계획, 사용자 **종료 보고**를 기록한다. **다음 단계 실행은 금지**.
4. 해당 항목이 완료되면 재현 증빙·코드 SHA·범위(합성/실물/독립)·사용자 **종료 보고**를 기록하고 그 항목만 `PASS`로 만든다. 바로 다음 항목 1개만 `READY`로 개방한다. 단계 마지막 체크가 PASS이면 다음 **단계 첫 체크**를 개방한다.
5. `python3 scripts/ire_checklist_gate.py verify --compare-parent`·회귀시험·GitHub Actions 재조회 후, 사용자에게 완료/차단 결과를 정확히 보고한다. **검증 CI 실패는 해당 체크 완료를 입증하지 못한다**.
6. 실물 영상 연구의 OPEN·비공개 원본·별도 사용자 2턴·금융 공식근거·V123/E4/E5·최종 KB HEAD는 [연구 종료 영수증](RESEARCH_RUN_CLOSEOUT_RECEIPT_TEMPLATE_20261122.md)에 별도 보존한다. 압축 JSON·개인 자료를 공개 repo로 옮기지 않는다.

## 5. 기존 기록의 PASS 처리

이전 E1 합성 구조·V6 deterministic 테스트 PASS는 참조용 배경 근거이지 **새 체크항목의 완료 도장을 자동 발급하지 않는다**. 현재 통합 브랜치에서 같은 SHA·계약으로 다시 재조회한 증거 및 사용자 보고가 있을 때 해당 항목만 PASS 가능. 실물 ETF E3 0/13, E5 실물 발행 0 기준은 별도 공식 영수증으로 변경되기 전까지 유지한다. 모든 단계가 종료되더라도 금융 자문/포트폴리오 공개·권고는 별도 적합성/법적 요건을 만족해야 한다.

**현 시작 상태:** `P0-0-01 READY`, `PASS 0/60`, `BLOCKED 59/60`. 첫 개발은 기준 동결/진실값 검증부터 시작하고, 부정확한 완료 표시를 금지한다.
