## 1. 범위와 원본 검증

- 현재 통합 브랜치의 [42개 전체 바이트·Git blob SHA·크기·원장 기록](IRE_P0_0_06_42_FILE_SECURITY_INVENTORY_20261122.json)을 실물 디렉터리와 전수 대조. V3/V4 25개 + V5 11개 + 비암호화 B64 6개를 42/42로 확인했다. 보관 중인 옛 파일이나 비공개 원문을 변경하지 않았다.
- 공개 `.json.zlib.b64` 6개를 **리뷰 코드 안에서만** 제한 크기로 복원·UTF-8 JSON 파싱했다. 복원된 값/문구는 GitHub Action 출력, Git, 보고서 어디에도 작성하지 않았다. 재현 가능한 숫자/해시만 기록.
- [SHA 고정 Python 보안 검사기](../scripts/ire_security_archive_gate.py) 및 [27개 양성·음성 방어 테스트](../scripts/test_ire_security_archive_gate.py): 공인된 42개 외 신규 `.b64`, SRT, SQLite, 개인 키 파일 또는 보관 ZIP의 Git 추적 경로 등록을 거부하고, 멀쩡한 등록 자료에도 파일 바이트/원장 해시 불일치를 허용하지 않는다. 이는 **push 이후 검사**이며 관리자 Ruleset 사전 차단을 대체하지 않는다.
- 시험 로그 범위는 Python 3.11.18 기반 동일 Git HEAD이고, 실제 개인 비공개 ZIP/SRT와 암호 키는 이번 공개 코드 실행에 제공하지 않았다.

### 공개 가역 파일 6개의 비내용형 실측 지표

- 파싱된 JSON **비압축 크기 합계 457,160바이트** — 고유 원자·고유 영상·고유 자막 수가 아님.
- 구조에서 감지한 소스/검토 관련 문자열 필드 **492개**, 길이 80자 이상 문자열 **54개**, 한글이 포함된 문자열 **181개**. 이것들은 규칙 기반 지표로 독립적인 금융 의미 판정이나 실제 기밀 문서 건수가 아니다.
- 따라서 **`공개된 데이터가 모두 무해하다` 또는 `비공개 정보 유출 0`이라고 인증할 수 없다.** 반대로, 독립 원문 대조 없이 금융 비밀이 확정 유출됐다고 과장하지 않는다. 공개 연구 파생 자료가 복원 가능한 사실 자체는 확정됐다.

## 3. 미해결 결함 및 권한

[파일별 결함 ID `P006-F01`~`P006-F42`와 공통 위험 `P006-R01`~`R06`을 이관한 중앙 HOLD 원장](IRE_P0_0_06_SECURITY_HOLD_DOCKET_20261122.json)이 단일 전수 기록이다.

- **P006-R01: 가역 자료 공개 적합성 불확정.** 비공개 저장소/금고 등 소유자 인가된 곳에서 실제 6개 파일의 원본·파생 여부를 사적으로 검토하고 기밀 원문/인용을 추출하거나 보고서에 재공개하지 않는다.
- **P006-R02: Git 과거 이력 노출.** 활성 브랜치에서 파일을 삭제해도 과거 커밋·다운로드·캐시에서 사라진다고 가정하지 않는다. 원본 개인 자료의 안전한 암호화 백업 확인 뒤 제거·이력 교정 가능성과 필요 범위를 별도로 심사한다. **`main` 변경·기존 98개 HEAD 보존을 깨는 무단 force-push/이력 재작성 금지**.
- **P006-R03: 25개 PPC1 실제 복구 미입증.** 소유자 키를 현재 공개 채팅/공개 저장소에 제공하지 말고, 소유자 제어 개인 실행 환경에서 `restore.py`와 원본 SHA256을 25/25 대조한다. 키 분실이면 복구 불가능할 수 있다.
- **P006-R04: 11개 V5 실물 복원 미입증.** 기존 개인 런타임 키·KDF·인증 태그 검증기를 합법적인 비공개 환경에서 확보해 원본 바이트 해시를 재검문한다. 키 없이는 보관물 무결성만 증명되고 연구 데이터로 전환 불가.
- **P006-R05: 기밀 무노출 검증 미완료.** 정확한 private original 대비 6개 공개 내용의 민감성 판정과 재사용 권한/개인 데이터 여부에 관한 증거가 없다.
- **P006-R06: 사전 접근 통제 부재.** 현재 CI는 신규 파일의 잘못된 public path를 탐지하지만 최초 공개 push를 차단하려면 GitHub 관리자 사전 Ruleset 및 별도 secret scanning이 필요하다. `main` 안전 정책을 완화하지 않는다.

## 4. 후속 조치 순서 및 PASS 전환 조건

1. **접근권한 확인과 보존:** 소유자가 인가한 비공개 저장 공간에 원본·복구 키가 **서로 다른 통제 하에** 존재하는지 확인. 기존 공개 Git에서 원본이 지워졌다고 오인하지 않는다.
2. **6개 공개 인코딩 자료 전수 기밀 판정:** 정확한 내용을 오프라인에서 분류하고, 민감 자료라면 먼저 안전한 암호화 사본과 실제 해시·복호화 복구 결과를 확인한다.
3. **공개 데이터 노출 대응:** 안전한 사본 확보 후 활성 브랜치·배포 경로에서 기밀 인코딩을 제거하거나 안전한 검증 영수증으로 대체하고 기존 코드 경로를 재검증. 과거 공개 history / 캐시의 위험을 별도 문서와 필요한 권한 절차로 처리한다.
4. **36개 아카이브의 실제 복구:** V3/V4 25개, V5 11개의 키·알고리즘·원문 SHA256 대조 결과를 비공개로 확보. 복구 실패·키 없음은 `HOLD`로 유지한다.
5. **최종 안전 심사:** 공개 적합성, 복구 가능성, 영구 노출 대응, 변경 사항의 동일 SHA 보안/전체 CI, 사용자 업무 종료 보고까지 충족되었을 때만 `P0-0-06 PASS` 검토. 그 전에는 `P0-0-07 BLOCKED`.

**현 단계에선 안전성 GO 없음.** `main` 변경, 신규 브랜치 생성, 비공개 자막 또는 키 공개, 미승인 E3/E4/E5·투자자문 승격 없음.
